◐ Learned

The runtime's CPU estimate

For the same 30 seconds, the runtime/metrics columns give about 0.67 cores, against the profile's 0.89. Window by window they swing from 0.07 to 2.7 cores at a steady 2,700 attempts a second. They're only meaningful averaged over minutes, and the profile is the number to trust.

The CPU profile

Where 0.89 cores went, by goroutine

Taken from t+24 s to t+54 s, during steady sending. Each bar is the share of CPU spent in that kind of goroutine, including everything it called.

What it means. Each delivery passes through several goroutines: generator → ReceiveEvents → dispatcher → lane worker → the HTTP client's write and read goroutines → the loggers. Every hand-off parks one goroutine and wakes another, often on another OS thread, and on Windows that wake-up (semawakeup, 12% by itself) is the single biggest item. This also explains run 54, where 200/s cost as much CPU as 785/s: at low rates nearly every event pays for a full wake-up. The work itself, writing requests to sockets, is under a fifth.
