Lanes That Grow on Demand

Run 49 again, with one change: the logger and the retry helper now wake up when a resize starts instead of sleeping through it. Resizes went from almost a second of standing still to no longer than one request. Analytics grew 40 → 80 lanes in its first 1.5 seconds and the fraud vendor 40 → 110 by t+4.4 s, then both stopped. For the first time at this rate nothing was refused: 33,520 delivered, plus 2 dead-lettered after six 500s from shared hosting. Both shared endpoints posted their best latency yet.

Next

Resizing is ready for a higher rate

  1. Stop paying for lanes nobody uses

    Memory went up, not because of growth, but because every lane buffer is now 200 slots and every retry channel 100. At 40 lanes × 1,140 endpoints that's about 110 MB set aside up front (heap 274 → 408 MB from run 48). Now that busy endpoints can grow, every endpoint can start small. The earlier per-class numbers (5 / 3 / 2 / 2) would cut both goroutines and those buffers by around 90%.

  2. Small clean-up in the new wait

    When the wake wins the select, the ticker isn't stopped. Recent Go versions collect it anyway, so it's harmless, but stopping it in both cases (or using time.After) is tidier.

  3. Step the rate up

    The generator's 1 ms sleep tops out near 780/s. Batch per tick to reach 1,200/s and then 3,000/s, with a longer trace (about 300,000 events at rate=3000) read while sending, so there's more than 5 seconds of peak to watch.
