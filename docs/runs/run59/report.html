Doubling Fixes the Ramp

Run 57 again, with lanes that double instead of growing by 10. Both shared endpoints now reach their 500-lane ceiling in 3–5 seconds instead of 6–19. Analytics delivered all 300,000, so the brief's "never lose an event" held. Refusals fell from 1,604 to 601, all at the fraud vendor, and every one of them fell on one of its seven resizes. The fraud vendor's p99 dropped from 14.8 s to 4.4 s. Two things didn't improve: the same ops-notifier delivery was dead-lettered after six 429s, and this run used about twice the CPU of run 57 for the same work, for a reason the data doesn't settle.

What's left to fix is the pause, not the growth. Each resize stops the dispatcher while it rehashes everything waiting, up to 6,048 deliveries for the fraud vendor. Analytics happened not to refuse because its bursts and its resizes didn't line up. With bigger queues for the shared endpoints (a few thousand slots) these pauses would be absorbed, and that's a one-number change. Starting the shared endpoints at 160 lanes would skip the first five resizes entirely.

CPU

Twice the CPU for the same work

Both profiles were taken during steady sending, after resizing had finished (run 57 at t+26–56 s, run 59 at t+24–54 s). The code running in that phase is the same in both runs, since doubling only changes the first five seconds. Absolute CPU-seconds in each 30-second window:

  • run 57 · 29.4 CPU-s
  • run 59 · 55.7 CPU-s

What the data says. The increase is almost all in the HTTP side: socket writes 5.7 → 12.1 s, response reads 2.9 → 7.2 s, lane workers 5.7 → 9.7 s, and scheduler time 7.6 → 14.2 s. It isn't connection churn (no new connections in either profile) and it isn't the resize code. Event intake (ReceiveEvents, the generator) actually used less. Writing the same requests to localhost taking twice the CPU points at the machine rather than the program. When checked after the run, the laptop was on battery at 1.6 of 1.9 GHz, and power saving or thermal limits would produce exactly this pattern. The retry helpers' NewTicker calls also grew (1.9% → 4.9%), mostly through garbage-collection assists triggered by allocating those tickers.

How to settle it: run again plugged in, with nothing else heavy running. Windows Defender scanning the growing CSVs is another candidate. If CPU drops back towards 1 core, it was the machine.

Next

Three small changes

  1. A bigger queue for the shared endpoints

    The remaining 601 refusals are resize pauses overflowing a 200-slot queue. A queue of a few thousand for endpoints that are allowed to grow (or for every endpoint, since a buffered channel of pointers costs 8 bytes a slot) absorbs them. Check the half-full admission rule too: with a bigger queue, "half full" means much more waiting.

  2. Stop counting 429s as attempts

    The same ops-notifier delivery is now dead-lettered on every run of this trace. A 429 should delay, not use up a retry.

  3. Rerun on mains power

    That settles the CPU question, and with the queue change it should be the first 3,000/s run with nothing refused.
